# Cloud Sync and the Cloud Sync Key — decided

_Decided 2026-10-23 (Ron + Claude Code, after three rounds of outside review by a fresh Claude.ai instance). Not built
yet. TODO task: "Cloud Sync: rename Relay, show one Cloud Sync Key, and 'make a new key' retires the old one" (Before

("credentials", "Channel ID", "passphrase")._

**The anti-bounce rule (Ron, 2026-10-23):** these names are decided. Only evidence reopens one — a real user misreading
it (a support email, feedback) — not a new argument. (No independent testers are available.)

---

## 1. Background

### What ReaderWrangler is

1. A free web app for organizing a large Kindle library: folders, lists, tags, searches. It runs entirely in the
   browser; there are **no accounts** (the landing page says so).
2. Books come in through a **bookmarklet**: the user clicks it while on Amazon.com, and it reads their library there.
3. The bookmarklet can't hand the data straight to the app (different websites), so it goes through **a small cloud
   mailbox** (a Cloudflare Worker): the bookmarklet drops the library in, the app picks it up, and the phone reads the
   library and the organization made on the computer. (Before the mailbox, the bookmarklet downloaded a file the user
   imported by hand.)
4. Everything in the mailbox is **encrypted on the user's device first**; the server only holds data it can't read.
5. Pre-launch; the user base is effectively one person (Ron). Rule 0: no shortcuts — get it right before launch.

### How it works today (checked in the code 2026-10-22/23)

1. Setup **generates two random values**; the user chooses neither:
   1. a **Channel ID** — a standard random ID (lowercase hex, 8-4-4-4-12 with hyphens). It's the mailbox address, and
      the server's only check: uploads, reads, deletes and device-state writes all go through on the ID alone (our
      architecture notes: "acts as access token for all KV operations").
   2. a **Passphrase** — 32 random letters and digits (A–Z, a–z, 0–9). With the ID it makes the encryption key:
      PBKDF2 over the passphrase, salt = SHA-256 of the ID **exactly as stored**, then AES-GCM-256. It never leaves the
      user's devices.
2. **One encryption key protects everything in the mailbox** — the uploaded library *and* the organization
   (device-state) the phone reads.
3. The two values always travel together: built into **the bookmarklet** (which hands them to the relay code through
   page-wide variables on Amazon's page); a **QR code** for the phone (a pairing web address carrying both); a **Copy**
   button (two lines); **two boxes** to type them in (computer and phone); and **saved backups**.
4. There is **one encryption build**: relay-crypto.js, reached through relay-client.js. The app, the phone and the
   bookmarklet's fetchers all load the same files (the bookmarklet's menu loads them from our site).
5. **Phone:** reads from the mailbox only; never writes.
6. **Incoming data isn't automatic:** the app checks in the background and shows a bar ("📡 New library data
   available …"); the user clicks to import.
7. **The relay already runs every route through one ID check, and "revoke" (with a proof) already blocks reads as well
   as writes.**
8. **What expires:** letters and device-state after 90 days; **the full library copy (generations + the pointer to the
   current one) never expires** — keep-newest-2 holds it; the revocation proof is permanent.

### The words users see today

Relay · Relay Setup · Import from Relay · Credentials (and "Save Credentials", "Regenerate credentials") · Channel ID ·
Passphrase · bookmarklet · Download Library / Collections (the bookmarklet's buttons on Amazon's page, repeated in the
app's setup steps) · Data Status · a Restore question about "a different sync channel" · the help text "These are *not*
your Amazon password. They are a channel ID and passphrase randomly generated by this app…".

About 80+ places (counted 2026-10-22): ~52 in the app, 3 on the phone, ~22 in the bookmarklet's own screens, ~13 on
the website pages.

## 2. The problems

1. **"Relay" is an engineering word.**
2. **Two values that are really one secret** — two things to copy, keep together and keep private, though never used
   apart and chosen by nobody.
3. **"Channel ID" is jargon, and "ID" reads as safe to share** — but the ID alone can write to or wipe the mailbox.
4. **"Library" is overloaded** — Amazon calls its side the library too, so a name with "Library" in it invites the
   wrong box for the Amazon password.
5. **One message overstates:** "Library data now syncs automatically through the cloud" — it waits for a click.
6. **Consistency "everywhere":** 80+ places plus every future dialog; RW's no-jargon rule is enforced by memory only.
7. **Found during the review — "Regenerate credentials" doesn't retire the old key.** It only replaces the key on this
   computer; the old mailbox stays open. Whoever holds the old key has both halves: they can read the current full copy
   (which never expires) and write to or wipe the mailbox — indefinitely.
8. **Found during the review — a silent "empty mailbox".** The relay's ID check ignores case but its storage doesn't:
   an ID in the wrong form is accepted and opens a separate, empty mailbox, and (because the salt is the exact ID) the
   key derived from it can't decrypt anything. The user would just see their data "gone".

### The key's format

1. **Shown** as `RW1-XXXXX-XXXXX-…` — the prefix, then **65 characters in 13 groups of 5**, plain ASCII hyphens (never
   other dashes), in capitals.
2. **The 65 characters:** the Channel ID's 32 hex digits (its hyphens dropped) + a **31-character secret** + **2 check
   characters**.
3. **Alphabet: Crockford's base32** — 0–9 and A–Z without I, L, O and U. Ron's experience decides it: O/0 and l/1 are
   the look-alikes that bite (floppy-disk keys); capital/small pairs aren't confused in print. Case-insensitive. The
   hex digits are inside the alphabet, so the whole key is one alphabet. 31 × 5 = 155 bits of secret (128 is the usual
   bar).
4. **Check characters:** ISO 7064's *pure* method, radix 32, modulus 1021 (the family of the IBAN check), computed over
   the whole string including `RW1`. Tested (§5): catches every single wrong character and every neighbor swap.
5. **New keys only.** Today's passphrases use a different alphabet; with one user there is no legacy path — Ron makes a
   new key once. Backups keep their two stored values; nothing reads today's two-line Copy text.
6. **Support code:** the **last 6 characters of the ID**, shown beside the key (not inside it) — safe to quote to
   support (24 bits of a 122-bit random ID). The relay's nightly operator email moves from 4 to 6 characters.

### Reading a key back — the one "tidy" step

1. **One function is the only way in** for a key or an ID: strip everything outside the alphabet (hyphens, spaces,
   line breaks, en/em dashes), fold to capitals, read O as 0 and I/L as 1, check `RW1` and the length, verify the check
   characters, split by position, check the ID half is hex, and **rebuild the ID in its exact stored form** (lowercase,
   hyphens at 8-4-4-4-12). A paste that isn't a ReaderWrangler key gets: "That doesn't look like a ReaderWrangler key —
   it's shown in Cloud Sync Setup on your computer."
2. **The key-making code refuses anything else** (an assertion, not a second tidy step — two tidy steps would drift).
3. **The relay refuses an ID not in that exact form** — its one ID check made strict (drop the case-insensitive flag);
   every real ID already passes. Fail loud, never a silent empty mailbox.
4. **A decrypt failure says so:** "This key doesn't match the data in Cloud Sync" — never "no data".
5. **The salt rule is a format commitment:** salt = SHA-256 of the canonical lowercase hyphenated ID. Changing the ID's
   canonical form later would silently change every key. Written into the security notes beside the key format.
6. **The bookmarklet builder bakes in the tidy ID.**
7. Tests: the round-trip (ID → key → ID, byte for byte); the check-character test (§5).

### "Make a new key" = change the locks

1. **Order — the user is never left without a working key:**
   1. make the new key;
   2. in one write: the new key becomes active, and the old ID + its revoke proof go into a **"pending revoke"** slot;
   3. revoke the old mailbox: **block, then delete** (letters, device-state, *and* the full copies + pointer, which
      never expire). "Already revoked" counts as success; **"proof rejected" is a bug — show it**, never treat it as
      done;
   4. clear the slot; rebuild the bookmarklet; show the QR code.
   If step 3 fails, retry at the next launch, with one honest line: "Your old key is still active until we can reach
   the server."
2. **Backups carry the pending-revoke slot**, so a restore on a wiped browser still finishes the job.
3. **Restoring an old backup** (made before the new key) brings back a key the relay now refuses. Say so: "This backup
   has an old Cloud Sync Key that was replaced — keep your current key." (Today's "different sync channel" question is
   the place.)
4. **The confirmation** (Ron's final word on copy):
   > **Make a new Cloud Sync Key?** Your current key will stop working. Your books and folders stay as they are. You'll
   > need to share the new key with your phone and other computers, and drag the new bookmarklet to your bookmarks bar.
   >
   > [Make New Key] [Cancel]

   "Stop working" becomes literally true; today it overstates. "Share" is deliberate — Ron: "I share my house key with
   my wife and any other residents. I still keep it safe. Never share and share only as needed are 2 different things."

### What we tell users

1. **Help line** (Cloud Sync Setup): "Your bookmarklet contains your Cloud Sync Key — it's saved wherever your browser
   saves bookmarks. Don't share it."
2. **Where the key is shown:** a line or tooltip "Your ReaderWrangler provided Cloud Sync Key"; the empty box's hint
   says the same (a hint vanishes while typing, so the `RW1` check above is the real guard against an Amazon password).
   Exact wording: Ron's word at build.
3. **Security notes and the security page:**
   - "Only the first part of your Cloud Sync Key goes to the sync server — to say which mailbox is yours. The rest
     encrypts your data and never leaves your devices."
   - What a leaked key exposes: **your book list and folders**, and the power to write to or wipe your Cloud Sync
     mailbox — not the library in your browser, not your Amazon login. The realistic holder of a synced bookmark is
     someone already inside your Google or Microsoft account.
   - The page-script risk, stated honestly (Ron, 2026-10-23):
     > The bookmarklet runs inside Amazon's page, so it trusts that page. Any script running there while it runs could
     > capture your Cloud Sync Key without you or us knowing. But a script in that position would already have your
     > Amazon session — everything you can do on Amazon — so your book list and folders are not the worst it could
     > take. If you know your key got out (you shared your bookmarklet, or lost a device), make a new key: that
     > retires the old one.
   - The support code: why showing 6 characters of the ID is safe.
4. The relay code deletes the page-wide variables after reading them — **tidiness only; never claimed as protection**
   (a hostile script could intercept the key on its way in regardless).

## 4. Considered and rejected

1. **Names for the key:** Sync ID (swaps one engineering word for another; "ID" reads shareable); User ID / Assigned
   User ID (implies an account; reads shareable; identifies a set of devices, not a person); Sync Key ("Sync" alone was
   obscure); Pair Key (ungrammatical); Pairing Key (runner-up — but the key also restores a cleared browser, which
   isn't pairing); Pair Secret ("secret" is engineering talk); Library Code / Pairing Code ("code" sounds casual);
   **Library Key** (the leaning until round 1 — it needed a "NOT your Amazon password" disclaimer, a sign the name
   invites the wrong reading).
2. **Splitting the key by length alone** (without check characters) — one lost character would shift everything
   silently. With the length check and check characters, splitting by position is safe, so no separator character is
   needed.
3. **Base62** (today's passphrase alphabet) — more look-alikes (l/I/1, O/0/o), case trouble typing on a phone and
   reading aloud, no published check method. **Base36** — keeps O/0 and I/1. **Crockford's own check symbols**
   (\* \~ $ = U) — outside the alphabet.
4. **The hybrid ISO 7064 check (MOD 33,32, one character)** — misses about 1 in 500 neighbor swaps (§5).
5. **A hash as the support code** — the last characters of the ID are just as safe (they can't be turned back into a
   122-bit random ID), already used by the nightly emails, and simpler.
6. **A bookmarklet that carries less** — it also *reads* from the mailbox (known books for incremental fetches, the
   current copy, pending uploads), so it needs a secret. Asking an open app tab for the key brings back the cross-site
   handoff the mailbox replaced; a two-key-pair design only moves the bookmarklet's private key — into the bookmark (no
   gain), amazon.com's site storage (readable by Amazon's scripts — worse) or an extension (RW isn't one).
7. **Changing the key on a schedule** (the only remedy for a leak nobody detects) — it would mean re-dragging the
   bookmarklet and re-pairing the phone every few months; too costly for this risk.

## 5. The check-character test (2026-10-23)

3,000 random keys; every possible single wrong character and every neighbor swap:

| Scheme | Single wrong character | Neighbor swaps |
| --- | --- | --- |
| Hybrid MOD 33,32 (1 check character, 64 data) | all 6,045,000 caught | 363 of 186,014 missed (0.195%) |
| **Pure MOD 1021, radix 32 (2 check characters, 63 data)** | **all caught** | **all 186,018 caught** |

No checksum smaller than its input catches every error: two separate mistakes slip through about 1 time in 1,021 —
and then the key simply fails to connect. Keep the test in the build as a permanent check.
