# Post-Mortem: 7.15.2 — Folders-header full-line right-click + accepted native-menu peculiarity

**Date**: 2026-09-21
**Release**: 7.15.2 (app), prod+dev, 2 alphas. Two things: (1) the FOLDERS section-header right-click
now covers the whole row (was just the word "Folders"); (2) a best-effort suppression of the native
browser context menu inside the left pane — which turned out to be an **intermittent browser
peculiarity we chose to accept and document** rather than chase. mobile.js untouched.

## The story: a bug we deliberately stopped chasing
The left-pane audit (Explore agent, read-only) mapped every row/header. Acting on it, the FOLDERS
full-line right-click was clean. The native-menu suppression was not: per-header `preventDefault`
no-ops leaked inconsistently; a container-level `preventDefault` on the whole left pane had **no
reliable effect**; and — the reframing clue — the leak hit **named folder rows that have working
custom menus**, and once the right pane (unreproducible). That combination means it is **not** a
handler-coverage gap: the `contextmenu` event or its `preventDefault` is intermittently not honored,
which is browser-level. Ron's call: accept it as a peculiarity, ship the suppression as best-effort,
and **record it in three places** (code comment at the suppressor, PRINCIPLES "Platform facts/Browser",
this PM) so no one re-investigates it later. CHANGELOG advertises only the reliable half (copy A) —
no promise the suppression can't keep.

## ✅ What worked
1. **NEVER ASSUME kept paying out — repeatedly, in one session.** I corrected three of my own
   assumptions against source: the `__library__` branch was "dead" (it's **live** — the FOLDERS header
   right-click), the FOLDERS header "lacked a `+`" (it **has** `+`/sort/collapse), and per-header
   no-ops "would suppress" (they **didn't**). Each was caught by reading/verifying, not shipped.
2. **Audit before acting.** The Explore map turned "which rows are right-clickable?" into a verified
   table, and it's what exposed that my TODO's "unwired / dead branch" note was wrong.
3. **Accepted the limitation honestly.** Shipped best-effort with a KNOWN-LIMITATION code comment and
   corrected my own inaccurate "never leaks" wording to "intermittent" — mechanical honesty (Law 12)
   applied to a comment, and the CHANGELOG doesn't over-promise.
4. **Recorded so it won't recur as an investigation.** Three homes, each for a different reader
   (the next editor of that code / the next person tempted by contextmenu suppression / the archive).

## ❌ What went wrong
1. **I spent alphas on the fix before instrumenting.** I proposed a `contextmenu` logger, but only
   after two failed suppression approaches; Law 3 (instrument first) would have said measure the event
   before the second approach. We stopped before actually instrumenting (Ron accepted the peculiarity),
   which is fine — but the order was fix-first, measure-later.
2. **Assumption density.** Three wrong assumptions in one small feature (above). All caught, none
   shipped — but they added cycles, and they're exactly why NEVER ASSUME got codified into CLAUDE.md +
   the gate + PRINCIPLES earlier the same day. The rule is young; the habit is still forming.

## 👀 Watch
- **The intermittent native-menu leak in the left pane** — documented + accepted. If it ever becomes
  reproducible or worse, the next move is instrumentation (document-level `contextmenu` logger, capture
  + bubble, `e.target` + `e.defaultPrevented`), not another blind `preventDefault`.

## Final thought
The useful outcome wasn't the code — it was deciding *not* to keep coding. A non-deterministic,
browser-level behavior is exactly the kind of thing that eats a day if you let "one more approach"
run; naming it, shipping best-effort, and writing it down in the three places someone would look is the
disciplined close. And the session was a live rehearsal of the rule it began by codifying: assume less,
verify more — three times the source said something other than what I'd have guessed.
