# Post-Mortem: 7.14.4 — cleared details stay cleared after Import

**Date**: 2026-09-20
**Release**: 7.14.4 (app), prod+dev, 3 alphas. One user-facing fix — a price goal / rating / tag /
note you deliberately cleared could come back on the next Import from Relay, and notes were never
actually preserved across an import at all. Under it: the per-book import merge was extracted into a
new `bookMerge.js` (a field-ownership registry + a pure `mergeBookFields`) and locked by a Node gate
test. mobile.js untouched.

The bug was small to state and the fix is a few lines of *behavior* — but Ron steered it into a
structural close-out of two recurring footgun classes, which is the real story.

## How it was found & what it turned out to be

1. **Real-use report.** Ron cleared price goals on four books he'd bought; a later Import brought them
   back. Filed as a data-integrity smell (Law-10 family), investigated on Ron's go.
2. **Root cause (goals):** branch 3 of the merge did `priceTrigger: book.priceTrigger ?? previousBook.priceTrigger`
   — `incoming ?? local`. A cleared value is `null`, which `??` reads as "absent, fall back to incoming."
   Incoming here is only a **stale echo of the app's own past push** (genuine restores skip this branch),
   so the cleared goal came back. The whole user-only cluster (goal + snapshots, rating, tags, note,
   target) had the same `??`.
3. **The fix flushed out a phantom (notes):** alpha.1 flipped the user cluster to local-wins. Ron
   re-tested — goal preserved, **note not**. The merge had been preserving a field called `note`; the
   real book field is `userNote` (the *backup* wire calls it `note`, and the merge had borrowed the
   wrong name). Notes had **never** been preserved on import — a latent bug hiding inside the fix for
   its sibling. Same class as the 6.12.0 `hidden`/`isHidden` (F4) phantom.
4. **Ron widened the mandate** from "fix what I reported" to "close the whole class — I didn't notice
   the others doesn't mean they aren't biting" **and** "eliminate the field-name-mismatch footgun that
   has gone off repeatedly." That produced the data-driven merge + the gate test, not a point patch.

## ✅ What worked

1. **The registry is the chokepoint.** `BOOK_FIELD_OWNERSHIP` names every merge-relevant field exactly
   once with its class; `mergeBookFields` is driven by it. Field names no longer live scattered across
   three hand-written merge branches — the exact condition that lets `note`/`userNote` drift.
2. **The "no-invented-keys" test invariant is a real mechanism for the phantom class.** A phantom target
   name (`note` for `userNote`) shows up as a key present on the merge OUTPUT but on neither INPUT. The
   gate test asserts that never happens — it would have caught both `note`/`userNote` and `hidden`/`isHidden`
   the moment they appeared. Cheap, pure-function, no production spam. Paired with a per-user-field
   clear-survives round-trip, both directions (missed field / invented field) are covered.
3. **Grounding before building paid off twice.** Reading the three branches in source (not from the
   summary) surfaced (a) branch 3 used `incoming ?? local` for `lastAmazonOwnershipType` while branch 1
   used local-wins — a real discrepancy the unified function had to resolve deliberately; and (b) branch 1
   silently **omitted** tags/userNote/isHidden entirely — a latent resurrection gap of the same class,
   closed for free by routing through `mergeBookFields`.
4. **Extract-to-pure-function made the gate possible.** The merge was inline in `saveBooksToIndexedDB`
   (needs IndexedDB). Pulling it into a dual-mode module (organizeEngine's pattern) made it Node-testable
   — the mechanism Ron asked for couldn't exist without the extraction.
5. **All edits on the branch → one squash delta → no branch-flip churn.** The 7.14.3 PM's headline
   friction (checkout-main→edit→commit→back for every doc/TODO edit) was avoided by doing version drops,
   CHANGELOG, and TODO on the fix branch and squash-merging code+docs together. Divergence pre-flight was
   clean (main == prod/main), so no reconcile needed.
6. **Scope boundary named, not hidden.** Branch 2 (owned + incoming-wishlist dup) keeps its distinct
   ownership-keep logic and wasn't unified; constants-everywhere wasn't adopted. Both were called out to
   Ron up front and filed in TODO the same breath.

## ❌ What went wrong / friction

1. **The phantom cost a round.** alpha.1 fixed the reported goal bug but I *wrote the fix using the
   phantom name* (`note: previousBook.note`) — carrying the old merge's mistake into the new code. It took
   Ron re-testing to catch it in alpha.2. I had the export's `note: book.userNote` / `userNote: item.note`
   mapping in view; a field-name cross-check against the actual write site during alpha.1 would have caught
   it before Ron did. **Lesson:** when fixing a field-*preservation* bug, verify each field NAME against
   its real setter/reader — the preservation site is exactly where names drift.
2. **The gate test only fully guards the branch-3 function.** Branches 1 & 2 route their user cluster
   through `assignUserOwnedFields` (names from the registry) and branch 1 through `mergeBookFields`, but
   branch 2 still has a small inline shape (`...existing`, `addedToWishlist`). The no-invented-keys
   invariant isn't asserted for branch 2's assembled object. Low risk (rare same-payload dup), filed.
3. **Compaction ate a reflex.** I over-explained the push convention ("which remotes? navigator changes?")
   that Ron knows I know cold (push = both, dev ≥ prod, local testing suffices unless Navigator/bookmarklet).
   A small tax, but a tell that post-compaction I rebuild known conventions from scratch. Re-saved to memory.

## 👀 Watch

- **Cross-device propagation is now explicitly a non-goal** for user-only fields (local always wins). If a
  real two-desktop workflow ever appears, this is the deliberate boundary to revisit (MULTI-INSTANCE §5).
- **The two remaining real-use finds** from 2026-09-20: context-menu clip (chokepoint all menus) and the

## Final thought
A one-line `??` fix became a two-footgun close-out because Ron refused to fix only what he'd noticed.
The durable win isn't that cleared goals stay cleared — it's that the merge now has a single place
where field behavior is declared and a test that fails loudly when a field name is invented. The phantom
that hid inside the fix is the proof it was needed: the same mistake, made twice in the same file, is
exactly what a mechanism (not a promise) is for.
