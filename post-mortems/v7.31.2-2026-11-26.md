# Post-mortem — 7.31.2 (2026-11-26): Regenerate's words tell the truth; a private way to report a weakness

_A patch release inside sprint 12 (outside reviews 2–4). Both changes come from outside review 2 (security): item 4
(Regenerate) and item 11 (public statements that aren't true). The full release run passed every tier on the committed
release (65 files, 494ede8) before the tag._

## What shipped

1. **The Regenerate box and the Security & Privacy page no longer say a new key shuts out the old one.** Making a new
   key leaves the old one working — on the old bookmarklet, the phone, and for anyone who has it — and the app forgets
   it, so it can't be revoked afterwards. Both now say: Revoke credentials & wipe relay first, then make a new one.
   (Ron's wording, 2026-11-25; built as 7.31.2-alpha.1 that day.)
2. **The page's Contact list links GitHub's private "Report a vulnerability" form** — Ron turned private vulnerability
   reporting on for the production repository the same day — so a weakness isn't posted on the public issue list.
3. **Documents, not the app:** `docs/reference/SECURITY.md` says at its top that parts are out of date, and its "never
   at risk, regardless of any scenario" is rewritten as the trust the bookmarklet asks for; the support notes (§2) say
   that regenerating leaves the old key working.

## What went right

1. **The release comb paid on its first day.** Item 11 added the security page and document to the release checklist's
   comb (CLAUDE.md); running the existing support-notes comb for "regenerate" in this release found the notes never
   said the old key keeps working — filled.
2. **Ron's questions kept improving the answers** — today items 9 ("why sign only small uploads?" → one rule for every
   write, less code) and 10 (his format number per cloud library). Ron asked for these cases to be recorded and kept:
   the log now lives in the Projects folder (`BETTER-IDEAS.md`), because it's about how we work, not about this app.
3. **Settings people can't see from the code were closed the same day:** private reporting, dependency alerts, secret
   push protection on both repositories, and a ruleset against force pushes and deletion (Ron's clicks).

## What went wrong

1. **A false, actionable sentence stayed live for a day after its fix was built.** 7.31.2-alpha.1 sat on main
   (2026-11-25 → 26) while the live page still told a person whose key got out that regenerating shuts it out. The
   reviewer had said "take it off the page now". **Lesson:** a fix to a false statement people act on is released at
   once, on its own, not held for the next release.
2. **My first ruleset advice wasn't enough to act on** — Ron: "is going to need a bit more direction". The second
   version gave the click path, every field, and which boxes NOT to tick (Restrict updates on a branch would block
   every push; Restrict creations on tags would refuse our own release tags), after checking GitHub's help page — which
   doesn't list the checkboxes, said so to Ron.
3. **Undefined words again** (item 9's first sentence: "every send leaves one batch"). Ron: "You lost me on the 1st
   sentence." Redone with "upload" and "stored item", each defined. The mechanism exists
   (`feedback_exact_verbs_and_stores`); this was a lapse in applying it to my own new words.

  the second on the committed release. No test can catch a false sentence on a page — the release comb is that check
  now (security page and document, every release).
