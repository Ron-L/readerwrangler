# Post-mortem — the CursorPopup positioning detour (7.18.0, alphas 24–32)

**Date:** 2026-09-30 · **Type:** process / debugging failure (mid-dev, no prod impact)
**Branch:** `feature/overlay-system` · **Cost:** ~8 alphas (25–32) and a long testing session, for a one-line bug.

## Summary

A right-click context menu (`rightPaneContextMenu`) opened with a large gap between the cursor and the
menu near the right border. The real cause was **one line in the trigger**: it pre-clamped the click with
a hardcoded menu-width guess (`if (x + 240 > innerWidth) x = innerWidth - 248`), which **pinned the click
x** to a constant for any click in the right ~240px — decoupling the menu from the cursor. The fix was to
delete that pre-clamp and pass the true `e.clientX/clientY`; `CursorPopup` already measures and positions
correctly. But I spent alphas 25–31 "fixing" `CursorPopup` — the innocent layer — before finding it.

## Timeline

- **24** — Built the `<Popover>` primitive, converted `rightPaneContextMenu` as proof. Gap reported.
- **25** — "Fixed" a shrink-to-fit theory by measuring at top-left. Made it worse. (Unconfirmed theory.)
- **26–27** — Added debug logging inside `CursorPopup`. Data showed `x:1186, gap:0` — "correct."
- **28** — `width: max-content` (a *real* latent fix for near-border squish — kept). Gap persisted.
- **29** — Switched flip→slide. Wrong; pushed the menu to the border.
- **30** — Reverted slide→flip (correct behavior — kept).
- **31** — Rendered a **magenta dot at the (x,y) the code positions from.** The dot was NOT at Ron's
  cursor → proof the *input coordinate* was wrong, not the positioning.
- **32** — Deleted the trigger's pre-clamp. Fixed.

## Root cause of the *bug*

`CursorPopup` was built (7.15.0) precisely to kill hardcoded size guesses — it measures the real menu and
flips/clamps to fit. But `rightPaneContextMenu`'s trigger still carried a legacy hardcoded pre-clamp from
before that, which ran first and pinned the coordinate. `CursorPopup` then faithfully placed the menu at
the wrong coordinate it was handed.

## Root cause of the *five-alpha miss* (the real lesson)

1. **I instrumented the consumer, not the source.** My probe logged the value `CursorPopup` *received* —
   already clamped by the trigger — instead of the raw `e.clientX`. So it kept certifying the innocent
   layer. **Instrument the origin (the raw event/state), never a value handed downstream.**
2. **I ignored the invariant tell.** `x:1186` appeared in *every* debug dump while Ron clicked different
   spots. A logged input that stays constant while the real input varies is proof you're measuring
   downstream. It sat in the first dump; I walked past it six times.
3. **Proximity / confirmation bias.** `CursorPopup` was the code under my hands, so I kept patching it.
   Each round's internally-consistent data confirmed that frame and dug me deeper.
4. **I had the rules and didn't apply them.** `feedback_debugging` Rule 2 ("after 3 alphas of edge-case
   patches, question the abstraction") and Rule 1b ("instrument → prove the theory") both existed. I
   violated both across five alphas. **The failure was application, not knowledge — passive memory did not
   fire mid-work.**

## Mechanism instituted (not a promise)

Because the only thing that reliably interrupts me mid-task is the pre-build gate, the wide net now lives
there:

- **`gate-check.py` item 12** — "3rd+ change chasing the SAME symptom → STOP, question the abstraction: is
  the bug even in the layer you keep patching? Go to the TRUE source; watch for a logged value constant
  while the input varies." Fires on every app-source edit; cannot be skipped.
- **`PRINCIPLES.md` Laws 3 & 4** — extended with this saga and the source-of-truth / invariant-value tell;
  Enforcement lines now cite gate item 12.
- **`feedback_debugging` Rule 1d** — the instrument-the-source sharpening + the note that Rules 2/1b
  existed but didn't fire, hence the gate.

## What survived as legitimate

`width: max-content` (kills the genuine near-border shrink-to-fit squish) and the right-edge flip (correct
VS Code-style behavior). Both stay; neither was the bug, but both were real improvements.
