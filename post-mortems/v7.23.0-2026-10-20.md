# Post-mortem — v7.23.0 (2026-10-20)

**The Relay deletes leftovers every night, and the app cleans up at each save without the one-hour wait.** Behind the
scenes only, so nothing changes for users. Released to prod and dev as squash `1a8c256`, tag `v7.23.0`; the branch
`feature/relay-delete` is kept. Both relays were redeployed from main at worker `7.23.0`, each with Ron's yes:
dev `2345bfe1`, production `75cacc83`. This was step 4 of the relay-storage plan. Work ran 2026-10-18 → 10-20:
alpha.1–2 on dev, two nights of dev deleting, then alpha.3 on both relays.

## What shipped

1. **Both relays delete what the daily check finds.**
   - Extra copies beyond the newest 2 finished ones go with no grace.
   - Unfinished copies go after 10 minutes.
   - Absorbed uploads go too.
   - The live copy and unimported uploads are never deleted.
   - Each run removes at most 20 keys and makes about 45 storage calls in all. Deletion order lets a run stop safely
     mid-item.
2. **The app applies the same rule at every save** (relay-client.js). A new commit check refuses a commit where the
   app's numbers and the worker's differ.
3. **The email names every key kind with its expected count**, and anything unexpected shows in red. Each blocked
   channel is classified by its own recorded reason. The deletion line says the limit counts keys while the list
   counts items.

## What went right

1. **Planted test keys, each labeled with the outcome it should get.**
   - On dev, 50 keys were planted: 20 were deleted, then 16 more, and 14 were kept, all exactly as labeled.
   - The "+1 day" unfinished copy was deleted on its own night (10-19), as predicted.
2. **The safety net proved itself on real data, unplanned.**
   - Ron's Tag from Collections testing ran on a branch still using the old one-hour app rule. It left 3 extra copies,
     and dev's nightly run removed them.
   - Dev's storage reading fell from 253.9 to 143.7 MB.
   - The account total fell from 48.4% to 37.4% of the free 1 GB.
3. **Production's first deletion was verified within minutes of the release, by hand, not left to the night.**
   - It deleted exactly `…21fc`, the Sep 9 torn save: 1 key, nothing else, no red lines.
   - All 53 of production's keys are now named; the old "other 27" is gone.
4. **"4 deleted, 7 used" was fixed before the release, not after.**
   - Ron spotted that the two numbers looked inconsistent.
   - The code confirmed that the limit counts keys while the list counts items.
   - The new wording was tested offline against four cases before anything was deployed.
5. **"Why not the worker?" was answered from the code and the design record.**
   - Ron asked why cleanup depends on the app. The answer is two cleaners, each covering what the other can't: the
     app at save time, and the worker nightly for torn saves and apps that never open again.
   - The record had no "why" for keeping cleanup in the app. I said so rather than invent one, and wrote the reasons
     down (RELAY-WRITE-REDESIGN §14a).
6. **The pre-build gate's batch refusal worked twice today, exactly as designed.**
   - Both of each batch's edits to app code were refused, and the re-send applied.
   - The PostToolBatch switch is holding.
7. **Main was merged into the branch before alpha.3.**
   - The branch predated last night's gate rebuild.
   - Only the two gate files conflicted. Both were resolved to main's tested version, and every tooling file was
     confirmed identical to main afterwards.

## What went wrong

1. **The help notes missed a release, and nobody noticed for four days.**
   - 7.21.3 changed Add Bibliography to Wishlist (every author tab, Kindle only, a Language panel), but the help notes
     never got an entry.
   - Their "up to date" stamp kept saying "through 7.21.2" while 7.21.3 and 7.22.0 shipped. The gap was visible, and
     no one read it.
   - This release's comb found it, and the entry was written now.
   - A stamp that nothing checks is a promise, not a mechanism (Law 12).
2. **The plan's "CHANGELOG: backend only" was stale by release time.**
   - `relay-client.js` is app code, and its cleanup rule changed.
   - Release prep caught this and the CHANGELOG got a second bullet.
   - This is Law 2's "a plan written days ago is an assumption" again.
3. **I edited TODO.md with a script instead of the Edit tool**, against my own standing rule.
   - The diff showed only the intended lines changed, so there was no harm.
   - It was still the method the rule exists to stop.
4. **The production switch needed Ron to ask twice.**
   - The automatic permission check stopped my first edit of `CLEANUP` as a production deploy.
   - I stopped and asked rather than work around it, and Ron then said "do both steps".
   - The check did its job; noted here so the extra round isn't mistaken for a fault.
