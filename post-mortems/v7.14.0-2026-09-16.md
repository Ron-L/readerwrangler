# Post-Mortem: 7.14.0 — the dead-end share, and the rule that should have already existed

**Date**: 2026-09-16
**Release**: 7.14.0 (app), prod+dev — 2 alphas. Replaces the auto-fire `mailto` "Email a Friend" with a **Share by Email** choice dialog (Open in email app / Open in Gmail (web) / Copy to clipboard). mobile.js untouched.

The trigger was a live failure Ron hit in his own daily use: "Email a Friend" auto-navigated to Gmail on the web and spun into `ERR_TOO_MANY_REDIRECTS`, with no way back — and, worse, **no way for RW to know it had happened** (the loop lives in another tab, cross-origin). A share path that can silently strand the user is a share path that has to stop guessing.

## The diagnosis that mattered

Several plausible theories died before the real one stuck (multi-account, URL length, session-settling, `window.open` vs anchor). The decisive isolation was Ron's: **the same Gmail compose URL loops when RW navigates to it, but works when he pastes it into the address bar and presses Enter.** That pins it to the browser's cross-site-initiator cookie boundary — a link *from another site* withholds some of Google's auth cookies, so Gmail loops trying to re-auth. **It cannot be fixed from a link.** The fix therefore isn't a better link — it's giving the user the choice we were making badly for them.

A late field observation refined the picture further: the **Windows native share sheet's** Gmail tile opens Gmail cleanly (OS-level app/protocol handoff carries the cookies), so `Share…` → Gmail is actually the superior Gmail path on Windows — better than our own in-app Gmail button. Captured for the KB.

## ✅ What worked well

1. **Ron's "stop theorizing" discipline, invoked at the right moment.** Four wrong theories in, he cut the speculation and demanded an isolation experiment. The one-line result (RW-nav loops, address-bar-Enter works) settled it in a sentence.
2. **The fix matched the diagnosis.** Once "unfixable from a link" was established, the design followed inevitably: offer the reliable path (desktop client), the caveated path (Gmail web, with the Enter workaround documented inline), and the never-fails fallback (copy). No attempt to out-clever the browser.
3. **Copy as the floor.** The always-works escape means no mail configuration can strand anyone — the property the old auto-fire lacked.
4. **Same-breath KB mining held.** SUPPORT-KB §11 (Share) and §19 (troubleshooting: redirect loop + no-mail-app) were updated *in the release*, not deferred — the release-checklist KB-comb step doing its job.
5. **Honest release numbering.** The de-numbering of the transactional-dialog references (it had been pre-assigned "7.14.0", then bumped by three intervening releases) killed a stale name-collision and a bad habit — planned work gets its number *when taken up*, per Ron.

## ❌ What went wrong

1. **The scar that recurred: alpha.1 shipped a new dialog with only Cancel + backdrop — no ✕, no Esc, and not registered in `anyDialogOpen`, so keystrokes leaked to the library beneath.** This is the *exact class* the 7.10.1 dismissal audit had just fixed across every existing dialog — but that audit was never turned into a forward *rule*, so the next new dialog reintroduced the defect. Ron's catch: "you did an audit… I thought you would have captured this as a rule… Did you fail to make a rule or just ignore it?" **Fix: the "New dialog/modal → the checklist" rule now lives in CLAUDE.md** (register in `anyDialogOpen`; add to `handleModalEsc`; ✕; backdrop). The comb then found **4 other pre-existing dialogs** missing from the registry — queued as the next fix release. Durable-chokepoint TODO filed: a shared `<Dialog>` that bakes in all four so the rule can't be forgotten.
2. **Sloppy word cost a round-trip: "menu order."** When recommending the button ordering, I called it "the menu order," but I was ordering the three buttons *inside the email dialog* — one level below the pre-existing `Share ▶` submenu (Copy Amazon Link / Email to a Friend / Share…, shipped in 6.10.0). Ron reasonably read "menu" as the top-level menu and thought a new menu level had appeared. It hadn't; only the *leaf* behavior of "Email to a Friend" changed. Lesson: name the exact surface (submenu vs dialog), especially when an old structure and new behavior share a word.
3. **Transport slip, self-caught.** The release commit was first written with a PowerShell here-string (`-m @'…'@`) inside the *Bash* tool, which passed a literal leading `@` as the subject. Caught immediately and amended with clean `-m` flags. The standing rule (Edit tool for content; never shell-quoted heredocs for message bodies) exists precisely for this — the reflex still reached for the wrong shell idiom.

## 👀 Watch

- **The registry-gap fix release** (next up): `newFolderHiddenAlert` (moderate), `autoOrgFileUnder` / `corruptionRecovery` / restore-loss (low). Register all four; then decide whether the shared `<Dialog>` chokepoint is worth building now or filed.
- **The native-Gmail finding**: fold into KB so the help-GPT steers Windows Gmail users to `Share…` → Gmail rather than the in-app link.
- **The "Open in Gmail (web)" button**: it carries the redirect caveat *inline*; if support traffic still lands on it, consider demoting or hiding it where a native share sheet is available.

## Final thought

The feature was small; the lesson wasn't. An *audit* fixes the instances that exist today; only a *rule* stops the class from coming back — and the gap between "we audited this" and "we made a rule about this" is exactly wide enough for the next new dialog to fall through. This release closed that gap in CLAUDE.md and, in doing so, surfaced four more dialogs the audit had never been asked about. Comb finds; chokepoint keeps — and a rule is the cheapest chokepoint there is.

## Addendum: 7.14.1 (same day) — the redirect hint gets a shortcut

A tiny same-day follow-up. The redirect-error hint under "Open in Gmail (web)" now leads with a guarded **Share…** link (shown only where `navigator.share` exists) that hands off to the OS share sheet — the same path as the `Share ▶` menu one level up, and often a *clean* Gmail route (a live finding: the Windows share sheet's Gmail tile doesn't hit the loop, because the OS hands off through the registered app rather than a cross-site link). The manual fallback was also clarified: the address-bar-Enter fix happens in the **new tab**, not RW's.

Process notes worth keeping:
- **Append-mode vs best-order, named by Ron.** He caught himself twice this cycle stacking "we need this too" requests without stepping back to sequence them ("I was just in append mode"). The value wasn't the items — it was pausing to ask *which order*, and separating the trivial Share note (7.14.1, ten-second visual test) from the harder registry-gap fix (four dialogs, two only reachable in failure states) into their own releases rather than bundling. Different test/risk profiles want different releases.
- **A short investigation that stayed short.** "Gmail vanished from the share sheet" got one honest hypothesis (it's a registered PWA target; Windows doesn't prune on a closed tab; probably scrolled or icon-misread) instead of a rabbit hole — and the answer was that Ron was looking for the Chrome swirl instead of the Gmail envelope-M. One step, checked in, done.
- **The B-informs-A discipline.** The "does Gmail reliably live in the native sheet?" uncertainty directly softened the A copy from "choose Gmail" (a false promise for non-PWA users) to "often has a working Gmail option." Let the open question shape the claim.
